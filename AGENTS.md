# Clipforge
Standalone English-language podcast/talking-head clipping SaaS. Never touch BrainrotAI's data, cloud resources, or repository. Never deploy or create live infrastructure without explicit approval. Always review Alchemy plans. Read `node_modules/effect/AGENTS.md` before writing Effect code; consult pinned Alchemy v2 source and official docs before changing resource declarations. Keep secrets out of source, logs and committed config. Tenant-scope every asset and state mutation. Schema-validate external input, use idempotency for jobs and billing. Render/media processing belongs in Containers, not Workers. Do not treat passing local fake-provider tests as verification of live provider integration.

## Session intent and safe autonomy
A session's deliverable comes from the user's brief: ongoing exploration, a read-only investigation/review, or an explicitly requested PR. **Do not turn every session into a PR.** Use a persistent session for long-term ownership when requested; it may investigate and run local experiments without being pushed toward a PR. Read-only investigations do not edit files by default. When coordinating several sessions, read `.agents/skills/clipforge-orchestrate/SKILL.md`. One writer per branch/worktree; do not remove a worktree with unmerged work or private evidence. For local env, follow `docs/worktree-env.md`: shared external local-only dotenv plus ignored per-checkout override; never copy `.local-dev/` or make staging credentials an automatic checkout default.

Unattended: local edits/tests/builds, worktrees, feature-branch pushes, and draft PRs are fine **when relevant to the requested outcome**. No DNS, cloud mutation, staging deploy, live email, Stripe checkout, paid inference, production release, or secret exfiltration without explicit prior authorization for that operation. Do not ask to decide reversible internal implementation details; choose a sensible approach and document trade-offs. If blocked by real external authorization, continue safe useful work and report the precise blocker without inventing a deliverable.

## When the requested outcome is a PR
Keep `main` clean; make independently reviewable PRs in feature worktrees. Read the feature map in `.agents/skills/clipforge-verify/references/feature-map.md`, reproduce the issue, add a regression, implement, run the verification skill, inspect the resulting UI/artifact, and review the **exact commit SHA**. Fix substantive review issues and repeat until checks pass; do not stop at a first slice or churn on speculative polish. A reviewer must not silently review an outdated SHA. Promote recurring findings into executable checks. If an external authorization blocks live acceptance, open a draft PR with passing offline evidence and a precise release gate. A PR is shippable **within its stated verification scope** when SHA-pinned checks and CI pass, relevant regression and user-facing behavior are checked, limitations are explicit, and the diff contains no credentials/fixtures. Offline shippable does not imply live-release-ready. Read `.agents/skills/clipforge-verify/SKILL.md` for the reproducible command and evidence contract.
