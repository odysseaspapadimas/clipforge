# Clipforge staging and operations

## Verified facts and design trade-offs

- Cloudflare Workers AI now hosts **Deepgram Nova-3 ASR** (not a Deepgram text or TTS model) with word timing and diarization: https://developers.cloudflare.com/workers-ai/models/nova-3/ . Its AI binding accepts `{audio:{body: ReadableStream,contentType:"audio/mpeg"},language:"en",diarize:true}` (Cloudflare's example: https://blog.cloudflare.com/workers-ai-partner-models/). Published HTTP price was **$0.0052/audio minute**, or ~$0.624 model charges for a 120-minute source, excluding Containers/R2/D1/Workflows. Chunk size is 60s/~0.5 MiB. **No Nova-3-specific maximum input duration or payload size is published on the model page**; the Workers AI platform lists 720 ASR requests/minute but not a separate per-request audio-duration cap (https://developers.cloudflare.com/workers-ai/platform/limits/). Worker inbound upload caps do not prove the Workers AI model's own limit. Actual account-specific AI request acceptance, diarized word response (speaker is described in the input docs but omitted from the generated output schema), latency, and timestamp behavior are **not yet tested**. Each chunk's speaker numbers reset; no speaker-to-face association is claimed. Chunk output is checkpointed; uncertain paid calls are not automatically retried. Workflow steps are capped at 30 minutes to respect Cloudflare's documented limit; real 2-hour media/Container turnaround remains unverified. When a chunk fails, minutes are returned but provider/compute usage is not refunded.
- Cloudflare-hosted Llama 3.3 70B can rank a bounded list of suggestions (max 900 output tokens; fallback to deterministic heuristics): https://developers.cloudflare.com/workers-ai/models/llama-3.3-70b-instruct-fp8-fast/ . No direct Deepgram or OpenAI credentials are required for the default path. Until the native contract is live-validated, the explicit `CLIPFORGE_TRANSCRIPTION_BACKEND=deepgram` option retains a separately keyed direct Deepgram Nova-3 fallback using the same ~0.5 MiB/60s audio chunks (not a 2h synchronous upload). A missing key fails closed, and Cloudflare errors never silently switch to this paid provider. Use `CLIPFORGE_DEEPGRAM_KEY` only with separate cost approval; stop/drain active Workflows before changing backends. Deepgram's 2 GB prerecorded limit and ~10-minute synchronous timeout are documented at https://developers.deepgram.com/docs/pre-recorded-audio/ . Whisper Turbo was considered but its documented output lacks the needed word-level timestamps and native diarization: https://developers.cloudflare.com/workers-ai/models/whisper-large-v3-turbo/ . AI Gateway remains optional pending actual observability needs; it is not a zero-cost substitute for inference.
- Cloudflare Email Service has a native `send_email` binding (https://developers.cloudflare.com/email-service/get-started/send-emails/) and Alchemy supports `Cloudflare.Email.SendEmail`: https://alchemy.run/cloudflare/email/send-and-receive/ . Staging must **onboard a domain for outbound Email Sending** before selecting `CLIPFORGE_EMAIL_PROVIDER=cloudflare`; Alchemy's binding descriptor does not create/onboard that domain. Cloudflare's current flow adds bounce MX/SPF/DKIM and DMARC DNS records, so do not onboard an unrelated production/staging zone without explicit approval. `CLIPFORGE_EMAIL_PROVIDER=resend` is available if a staging sender domain cannot be onboarded; its provider credentials/delivery still require verification. Local development logs links to ignored `.local-dev/` and never sends real mail. Verification/reset callbacks await the delivery attempt, rather than silently swallowing errors.
- Worker inbound request size depends on zone plan (100 MB Free/Pro; 200 MB Business; https://developers.cloudflare.com/workers/platform/limits/). Upload parts are 32 MiB, Worker memory 128 MiB. Container `standard-2` is 1 vCPU/6 GiB RAM/12 GB disk; image disk and max 2 instances, 20-minute FFmpeg subprocess budget, 5 GiB source, 2h recording and 512 MiB export cap must be load tested: https://developers.cloudflare.com/containers/platform/limits/ . Container CPU/disk/idle and Workflow step/state usage have billable limits even with no AI calls. D1 has a **100-bound-parameter limit per statement** (https://developers.cloudflare.com/d1/platform/limits/); transcript inserts use 14-word statements in 25-statement batches.
- Stripe catalog, Checkout, Portal and webhook delivery use **Alchemy v2's built-in Stripe provider**. https://alchemy.run/stripe/setup/ confirms `sk_test_` creates *real* Stripe test-mode resources. The stack rejects anything except stage `staging` with `STRIPE_API_KEY=sk_test_…`; this does not by itself verify the key/account or prevent resource creation. $29/month / 120 source minutes is provisional. Webhooks should be tested for invoice/payment ordering, renewal, failure, cancel and reconciliation before opening signup. The provider object wrapper lacks original webhook event ID/timestamp; terminal cancellations and stale Checkout completions are now guarded, but monitor reordered renewals and reconcile with Stripe before public release.

## Current preflight and blockers

Cloudflare identity preflight completed against the default OAuth profile; its account ID matches the expected TEST staging account configuration in BrainrotAI's `.staging.env` (read-only). Its `STRIPE_SECRET_KEY` has `sk_test_` prefix; a read-only Stripe `/v1/account` GET confirmed the returned account ID matches `EXPECTED_STRIPE_ACCOUNT_ID`. Alchemy resolves the TEST key from ephemeral `STRIPE_API_KEY` environment credentials, so no Stripe profile mutation is needed. A **single** `bun alchemy --no-input plan --stage staging --profile default --detailed` completed on this account: **12 creates, 27 binding changes, no updates/deletes**; names are all Clipforge-specific and not BrainrotAI's. The plan output is in ignored, mode-0600 `.local-dev/staging-plan-preflight.log`. This was a preflight with intentionally invalid `.invalid` sender/origin placeholders, **not an approved deployable configuration**. The stack now rejects such placeholders during subsequent plans, requires two distinct long secrets, and limits the Cloudflare email binding to its configured sender address. No staging Worker/Container/D1/R2 was deployed, no Stripe resources created, and no paid model calls were made. Never use BrainrotAI's LIVE `.prod.env` or modify BrainrotAI resources.

The staging web app now has a fixed, separate Worker name `clipforge-staging-web`; serve it at `https://clipforge-staging-web.<account-subdomain>.workers.dev` (`odysseas-patra` was observed on the connected account). **workers.dev solves hosting, not outbound email**: Cloudflare Email Sending still requires onboarding a sender domain in the account; workers.dev is Cloudflare's domain, not a user-owned sender zone. Do not present sign-up as functional without delivery and verification. To proceed safely, use a dedicated authorized email sender domain or independently verified Resend sandbox credentials; do not silently reuse BrainrotAI's domain/DNS. Set `CLIPFORGE_APP_ORIGIN` to that exact HTTPS Clipforge Worker origin and `CLIPFORGE_EXPECTED_CF_ACCOUNT_ID` to the preflighted 32-hex account ID (the stack verifies the resolved OAuth/profile account before resource registration), and persist independent random `CLIPFORGE_AUTH_SECRET` (>=32 chars) and `CLIPFORGE_INTERNAL_SECRET` only in a local secrets manager, never git/chat. Ephemeral plan secrets must **not** be used for deployment or rotated unknowingly afterward. These are env names only; never commit values. A **separate $3 total Clipforge paid STAGING model-inference allowance is now approved** (not part of other projects' budgets). The `inference_spend` D1 ledger atomically caps all staging projects at **10 total source minutes**, never refunds uncertain paid inferences, and fails/refunds customer credits before any AI call when exhausted. At the published Nova HTTP rate this caps estimated transcription charges near $0.052 plus a small bounded Llama ranking call; it is deliberately far below $3, not a guarantee of Cloudflare's actual bill. Start with a single <=60-second recording, inspect actual usage/billing, and stop if costs cannot be verified; do not enlarge the cap without separate review. Staging provisioning has infrastructure cost even with zero inference; check Cloudflare billing/quota and user approval. Before deployment, replace the previously planned placeholder sender/origin with verified values (the stack now rejects reserved placeholder domains and enforces its own workers.dev hostname), run the plan again with the same environment/secrets intended for apply, review the full diff (account ID, stage names, TEST Stripe resources, public routes, Container size, migrations and R2 lifecycle) and ensure **no unrelated edits/deletions**. Only then deploy the same reviewed stage/profile. A plan is read-only when its state store already exists and `--no-input` rejects bootstrap prompts; do not add `--yes` without separately inspecting its state-store upgrade/bootstrap side effects. No production merge, deployment or live-billing provisioning is authorized.

When deployment and a Clipforge inference allowance exist, use a **short, consented real spoken interview**. Sign up with a real verified mailbox, complete Stripe **TEST** checkout/card, confirm paid invoice grants the configured minutes exactly once, upload a video, watch real Workers AI progress, compare stored word transcript to the audio, inspect actual candidate selection, edit framing/captions, export via deployed Container, download and ffprobe the MP4; then try another account and check denial. Measure actual per-stage costs and latency. Only that sequence is a verifiable staging journey. No screenshots or offline fakes count as a substitute.

## Local validation

Install Bun 1.3.14, FFmpeg, Docker and Playwright Chromium. `bun install`, `bun run typecheck`, `bun test test renderer`, `bun run build`, `bun run test:e2e`. `bun run dev` + `bun run dev:renderer` starts a **clearly labeled offline sandbox**, not a staging simulator: it uses SQLite/files, fixture words and fake billing, while running real FFmpeg MP4 export. No API tokens or cloud resources are needed for these tests. An actual `docker build -t clipforge-renderer:staging-check renderer` and POST `/prepare-chunks` extracted 3 chunks from 126 seconds. A second local Docker extraction of a 7,199-second video produced **120 ordered chunks, largest ~480,531 bytes**, using the streaming NDJSON parser without buffering the full recording. These validate local FFmpeg segmentation and bounded transport, not the Workers AI model's input acceptance or output accuracy.

Monitor outstanding Workflow jobs, invoice grants, minute reservations/releases, audio chunk progress, failed inference/export and Container cold-start. Source and output R2 objects are private and expire 90 days after individual creation; D1 metadata may outlive media, so disclose expiry and add deletion/account-data handling before a public release. Two active uploads per account and two Container instances are configured. A D1-backed, two-slot admission table now serializes cross-account prepare/export work onto stable `media-slot-0` and `media-slot-1` Container IDs; Workflows wait durably (20-second sleeps for up to 30 minutes), re-check generation-fenced leases, and release them in `finally`. Leases expire after 31 minutes if a Worker crashes; each Container also rejects a second overlapping FFmpeg job with HTTP 429. Local SQLite concurrency tests and a real local Docker overlapping-request test passed (429 while busy, 200 afterward). Cloudflare service-binding, D1 transactional ordering, lease expiry and stalled jobs still require staging verification; failures return customer source minutes where applicable. Per-account active/daily job checks are best-effort under races; credit reservation is atomic per D1 statement. Canceled subscriptions cannot be revived by duplicate paid invoices, late same-ID subscription updates or old Checkout completions; a single database claim controls first Stripe customer creation, with ambiguous outcomes deliberately requiring operator reconciliation. Failed export Workflows have an explicit guarded restart path; live Cloudflare restart semantics still require staging verification. Cloudflare production-side binding behavior, billing event ordering, mail deliverability, quota and per-account costs are unverified until guarded staging exercises them.
